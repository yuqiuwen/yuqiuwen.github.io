核心分界线：

  • Workflow（工作流）：流程由代码预先定义，LLM 只负责节点内的任务，可控、稳定、成本低。
  • Agent（智能体）：LLM 动态决定下一步做什么、用什么工具，灵活但不可预测、成本高。

二、单 Agent：推理与行动模式

1. ReAct（Reasoning + Acting）

flowchart LR
    Q[用户问题] --> T[Thought 思考]
    T --> A[Action 调用工具]
    A --> O[Observation 观察结果]
    O --> T
    T --> F[Final Answer]
  • 思想：边想边做，每一步根据上一步的观察结果决定下一步。
  • 场景：问答、搜索、简单工具调用、客服。
  • 优点：简单通用，适应性强，可解释。
  • 缺点：步步调用 LLM，成本高；容易陷入循环或短视。

2. Plan-and-Execute（先规划后执行）

flowchart LR
    Q[任务] --> P[Planner 制定计划]
    P --> E[Executor 逐步执行]
    E --> R{需要重新规划?}
    R -- 是 --> P
    R -- 否 --> F[输出结果]
  • 思想：规划与执行分离，可用大模型规划、小模型执行。
  • 场景：长链路任务，如研究报告、数据分析、自动化运维。
  • 优点：全局视角强，执行阶段可用小模型降本。
  • 缺点：计划可能不合理，需要 replan 机制。

3. ReWOO（Reasoning WithOut Observation）

flowchart LR
    Q[任务] --> P["Planner 一次性生成计划，含变量占位 #E1 #E2"]
    P --> W[Worker 批量执行工具]
    W --> S[Solver 汇总证据生成答案]
  • 思想：规划时不等待工具结果，用变量占位，最后统一汇总。
  • 场景：步骤相对确定、对 token 成本敏感的任务。
  • 优点：LLM 调用次数少，省 token，可并行。
  • 缺点：无法根据中间结果动态调整。

4. CodeAct（以代码为行动）

flowchart LR
    T[LLM 生成代码] --> S[沙箱执行]
    S --> R[执行结果/报错]
    R --> T
  • 思想：用可执行代码代替 JSON 工具调用，一次代码可组合多个操作。
  • 场景：数据分析、自动化脚本、编程 Agent、复杂计算。
  • 优点：表达力强，可组合逻辑（循环、条件）。
  • 缺点：需要安全沙箱，有安全风险。

5. ToT / GoT / LATS（树/图搜索式推理）

flowchart TD
    R[问题] --> A[思路A]
    R --> B[思路B]
    R --> C[思路C]
    A --> A1["A-1 ✗ 剪枝"]
    A --> A2["A-2 ✓"]
    B --> B1["B-1 ✗ 剪枝"]
    A2 --> Z[最终解]
  • 思想：同时探索多条推理路径，评估、剪枝、回溯（LATS 结合 MCTS 蒙特卡洛树搜索）。
  • 场景：数学推理、规划类难题、代码生成、游戏、需要探索的任务。
  • 优点：解题成功率高。
  • 缺点：成本很高，延迟大。

三、自我改进模式

6. Reflection / Reflexion / Self-Refine

flowchart LR
    G[Generator 生成] --> C[Critic 批评/评估]
    C -- 反馈 --> G
    C -- 通过 --> O[输出]
    C -.-> M[(反思记忆)]
    M -.-> G
  • Self-Refine：同一个模型生成、批评、改进，不依赖外部信号。
  • Reflection：独立的 Critic 角色给出反馈。
  • Reflexion：把反思结果存入记忆，用于后续尝试，适合多轮试错。
  • 场景：代码生成（结合单测反馈）、写作润色、复杂推理。
  • 缺点：增加延迟与成本；自我评估不可靠时可能原地打转。

四、工作流编排模式（Anthropic 总结的五种）

7. Prompt Chaining（提示链）

flowchart LR
    I[输入] --> S1[步骤1] --> G{校验 Gate} --> S2[步骤2] --> S3[步骤3] --> O[输出]
    G -- 失败 --> X[终止/重试]
  • 场景：任务可清晰拆成固定子步骤，如"生成大纲→校验→写正文→翻译"。
  • 特点：用延迟换准确率，每步更简单。

8. Routing（路由）

flowchart LR
    I[输入] --> R{Router 分类}
    R -- 类型A --> A[专用处理A]
    R -- 类型B --> B[专用处理B]
    R -- 类型C --> C[专用处理C]
  • 场景：客服分流（退款/技术/咨询）、按难度选择大小模型。
  • 特点：关注点分离，每个分支可深度优化。

9. Parallelization（并行化）

flowchart LR
    I[输入] --> T1[子任务1]
    I --> T2[子任务2]
    I --> T3[子任务3]
    T1 --> AG[聚合]
    T2 --> AG
    T3 --> AG
  • Sectioning（分段）：独立子任务并行，如多文档摘要、内容审核与回答同时进行。
  • Voting（投票）：同一任务多次执行取共识，如代码漏洞审查、提升可信度。

10. Orchestrator-Workers（编排者-工作者）

flowchart TD
    I[任务] --> O[Orchestrator 动态拆解]
    O --> W1[Worker1]
    O --> W2[Worker2]
    O --> W3[WorkerN]
    W1 --> S[Orchestrator 综合结果]
    W2 --> S
    W3 --> S
  • 场景：无法预知子任务数量的任务，如跨多文件的代码修改、多源调研。
  • 与 Parallelization 的区别：子任务是动态生成的，而非预定义的。

11. Evaluator-Optimizer（评估者-优化者）

flowchart LR
    G[生成] --> E{评估}
    E -- 不达标+反馈 --> G
    E -- 达标 --> O[输出]
  • 场景：有明确评价标准的任务，如文学翻译、复杂搜索、代码质量迭代。
  • 与 Reflection 的关系：本质相同，前者强调工作流中的固定循环，后者强调 Agent 的自我反思能力。

五、多 Agent 协作模式

12. Supervisor（监督者/中心调度）

flowchart TD
    U[用户] --> S[Supervisor]
    S <--> A[Agent A 研究]
    S <--> B[Agent B 写作]
    S <--> C[Agent C 代码]
    S --> U
  • 特点：中心化调度，所有通信经过 Supervisor。
  • 场景：角色分工清晰的任务，如研究+写作+审核。
  • 优点：可控、易调试。缺点：Supervisor 是瓶颈和单点。

13. Hierarchical（层级式）

flowchart TD
    T[顶层 Manager] --> M1[中层 Team Lead A]
    T --> M2[中层 Team Lead B]
    M1 --> W1[Worker]
    M1 --> W2[Worker]
    M2 --> W3[Worker]
    M2 --> W4[Worker]
  • 特点：多层 Supervisor，树状结构。
  • 场景：大型复杂项目，如软件开发团队（PM→架构→开发/测试）。
  • 优点：可扩展，上下文隔离。缺点：层级过深导致延迟高、信息损耗。

14. Swarm / Handoff（群体/交接）

flowchart LR
    U[用户] --> A[分诊Agent]
    A -- handoff --> B[销售Agent]
    B -- handoff --> C[支付Agent]
    C -- handoff --> D[售后Agent]
    B -- handoff --> A
  • 特点：去中心化，Agent 自己决定把控制权交给谁（OpenAI Swarm / Agents SDK）。
  • 场景：客服流程、对话型多阶段业务。
  • 优点：轻量灵活。缺点：全局流程难把控，容易乒乓交接。

15. Debate / Critic（辩论/评审）

flowchart LR
    A[Agent 正方] <--> B[Agent 反方]
    A --> J[Judge 裁判]
    B --> J
    J --> O[最终结论]
  • 场景：事实核查、决策分析、复杂推理、减少幻觉。
  • 缺点：Token 消耗大，可能出现从众效应。

16. Blackboard（黑板模式）

flowchart TD
    BB[(共享黑板 Blackboard)]
    A1[专家Agent1] <--> BB
    A2[专家Agent2] <--> BB
    A3[专家Agent3] <--> BB
    C[控制器] --> BB
  • 特点：Agent 不直接通信，通过共享空间读写信息，谁能贡献谁就行动。
  • 场景：问题解法不确定、需要多专家增量贡献，如复杂诊断、情报分析。

模式核心典型场景

七、核心对比表

1. 单 Agent 推理模式对比

模式规划方式LLM调用次数灵活性成本适用任务
ReAct边做边想多⭐⭐⭐⭐⭐中高探索性、不确定任务
Plan-and-Execute先整体规划中⭐⭐⭐中长链路、结构清晰任务
ReWOO一次性规划+占位少⭐⭐低步骤确定、成本敏感
CodeAct以代码行动中⭐⭐⭐⭐中计算/数据/编程
ToT / LATS多路径搜索极多⭐⭐⭐⭐很高高难度推理
Reflection生成-批评循环多⭐⭐⭐中高质量要求高

2. 工作流模式对比

模式流程是否预定义核心价值典型例子
Prompt Chaining完全固定拆解降低难度大纲→正文→润色
Routing分支固定分流、专业化客服分类
Parallelization并行结构固定提速/提升置信度多维度审核、投票
Orchestrator-Workers子任务动态处理不可预知拆分多文件代码改动
Evaluator-Optimizer循环结构固定迭代提质翻译、代码优化

3. 多 Agent 模式对比

模式控制方式通信方式可控性扩展性适用场景
Supervisor中心化星型高中分工明确的团队任务
Hierarchical分层中心化树型高高大型复杂项目
Swarm/Handoff去中心化点对点交接低中对话流程接力
Debate对抗+裁判多轮互相辩论中低决策、核查
Blackboard共享状态驱动间接通信中高解法不确定的协作

八、易混淆概念辨析

对比区别
ReAct vs Plan-and-ExecuteReAct 走一步看一步，适应性强；P&E 先有全局计划，更适合长任务，但要处理计划失效。
Plan-and-Execute vs ReWOOP&E 每步执行后可能重规划；ReWOO 规划一次后不看中间结果，直接批量执行。
Reflection vs Evaluator-Optimizer思想一致。前者偏 Agent 自省，后者偏工作流中的评估循环。
Parallelization vs Orchestrator-Workers前者子任务预定义；后者由 LLM 动态拆解。
Supervisor vs SwarmSupervisor 中心调度；Swarm 由 Agent 自主交接，无中心。
Workflow vs AgentWorkflow 由代码决定流程；Agent 由 LLM 决定流程。
Orchestrator-Workers vs Supervisor前者通常是单次任务内的动态拆分，Worker 无独立身份；后者是多个有独立角色和能力的 Agent。

flowchart TD
    S[开始] --> Q1{单次 LLM 调用+RAG+工具 能解决?}
    Q1 -- 是 --> R1[直接使用 Tool Use / RAG]
    Q1 -- 否 --> Q2{流程是否可预先确定?}

    Q3 -- 并行 --> W2[Parallelization]

    Q2 -- 否 --> Q4{单个Agent上下文/能力足够?}
    Q4 -- 是 --> Q5{任务特点}
    Q5 -- 探索性 --> A1[ReAct]
    Q5 -- 长链路 --> A2[Plan-and-Execute]

    Q5 -- 计算/编程 --> A4[CodeAct]

    Q6 -- 流程接力 --> M3[Swarm / Handoff]
    Q6 -- 需要多视角 --> M4[Debate]
